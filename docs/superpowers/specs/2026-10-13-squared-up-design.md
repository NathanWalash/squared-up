# Squared Up: design spec

Date: 2026-10-13 (revised the same day: scope simplified)

## Goal

Learn Azure and Terraform by building and deploying a small real app, one lesson at a time. The learner writes the code and infrastructure. Claude guides, explains and reviews, and does not write the solution unless asked. The app is a vehicle for the infrastructure, so it stays as simple as possible.

## Approach: thin slice first, then layer on

Get the simplest possible kanban deployed to Azure with Terraform. Only then add features and services, one stage at a time, each as a small lesson.

## Stages

### v1: simple kanban, deployed

- A board with three columns: To do, Doing, Done.
- Add a card (title), move it between columns with buttons, delete it.
- Cards stored in PostgreSQL.
- No sign-in yet. The URL is not shared, and the stack is destroyed between sessions (see risks).
- Deployed to Azure Container Apps entirely from Terraform.

### v1.1: recurring and scheduled cards

- Cards can recur on a schedule (weekly, monthly and so on), for example a bill.
- A scheduled **Container App Job** (cron, daily) does two things:
  1. **Spawns** the next occurrence of each recurring card as an "Upcoming" card, if one does not already exist.
  2. **Promotes** cards whose date has arrived from "Upcoming" to "To do" (for example "pay the energy bill").
- Both steps must be **idempotent**: safe to run twice without creating duplicates.

### Later

- Sign-in (Entra, with GitHub as a fallback)
- Key Vault and managed identities for secrets
- App Insights and alerts
- Private networking and CI/CD (GitHub Actions with OIDC)
- Receipts and proof (Blob Storage), OCR (Document Intelligence), email reminders, splitting payments between flatmates

## Tech stack

- TypeScript, Next.js (App Router), Server Actions with Zod validation
- Prisma and PostgreSQL
- Docker, one container for the app

## Azure services for v1

- Resource group, with tags (done)
- Log Analytics workspace (needed by the Container Apps environment)
- Container Registry (ACR), with a user-assigned managed identity that can pull images
- Container Apps environment and the web app
- PostgreSQL Flexible Server and one database
- The database password is generated by Terraform and passed to the app as a Container App secret for now. It moves to Key Vault later. The state file therefore holds a secret, which is acceptable because it lives in a private container with Azure AD access only.

## Terraform

- `azurerm` provider, with `resource_provider_registrations = "none"` (providers registered by hand)
- Remote state in Blob Storage with locking, in its own resource group (`rg-squaredup-tfstate`)
- Local modules, introduced as real resources need them: monitoring first, then registry, app and database
- Budget alert (done)
- `terraform destroy` at the end of a session for anything that bills hourly (notably Postgres)

## Environment

- Personal Azure free account ($200 credit, 30 days), subscription "Azure subscription 1", personal tenant
- Region: uksouth, or the nearest region that works
- Patterns may be borrowed from the work project's infrastructure, but no code is copied from it

## Learning method

Each lesson follows the same loop: concept, write, plan, apply and inspect in the portal, commit. Break and fix something deliberately now and then. One git commit per lesson. Building bottom-up means errors have a single cause.

## Lesson roadmap (v1)

1. Terraform basics: provider, backend, resource group (done)
2. Variables, locals, outputs, tags, budget alert (done)
3. First module: Log Analytics workspace
4. Container Registry, a managed identity that can pull, and a hello-world image pushed
5. Container Apps environment and app: hello-world live in a browser
6. PostgreSQL Flexible Server and database
7. Build the simple kanban locally (Next.js, Prisma, local Postgres in Docker). Can be started any time.
8. Dockerfile, push the real image, run migrations, deploy: v1 is live

Then v1.1 (the scheduled job) and the "Later" items, one lesson each.

## Done when (v1)

- `terraform apply` builds everything from a clean state and `destroy` removes it.
- The kanban is reachable at the Container App's URL, and cards persist in Postgres.
- The learner can explain what each service is for and why it is there.

## Risks

- No sign-in in v1 means anyone with the URL could edit the board. Mitigation: do not share the URL, keep the board free of real data, destroy the stack between sessions, and add sign-in as the first "Later" item.
- Next.js, Prisma and Azure all being new at once, so the app stays minimal and its build is lesson 7.
- Free-account region or SKU restrictions.
- Postgres bills hourly, so it is created late and destroyed at the end of each session.
- Log Analytics workspaces are soft-deleted for 14 days, so recreating one with the same name after a `destroy` can fail. There is a provider setting for permanent deletion on destroy.
